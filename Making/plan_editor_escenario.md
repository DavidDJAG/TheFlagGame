# 2D Map Editor Development Plan

## 1. Goal

Design and implement a **2D canvas-based map editor** for a multiplayer capture-the-flag style game, where the developer can:

- define a **hard perimeter** that contains players
- create and edit **closed polygon objects**
- create and edit **rectangles**
- create and edit **circles**
- place the **two flags** in their starting positions
- **select and delete** objects
- **save** the map as **JSON**
- **reload** a previously saved JSON map
- leave the map ready for the **game system** to load and send to clients

The intended approach is simple, maintainable, and compatible with an **HTML + JavaScript/CSS** frontend plus a **C# .NET 9** game backend.

---

## 2. Functional scope

### Required features

1. **2D canvas with grid**
2. Tool to define a **hard map perimeter**
3. Tool to create **rectangles**
4. Tool to create **circles**
5. Tool to create **closed polygons**
6. Tool to place:
   - blue flag
   - red flag
7. **Selection** of existing objects
8. **Deletion** of objects
9. Panel with minimum properties:
   - `id`
   - `type`
   - coordinates
   - dimensions or vertices depending on type
10. Export to **JSON file**
11. Import from **JSON file**
12. Basic map validation

### Recommended features

1. **Grid snap**
2. Dragging existing objects
3. Vertex editing for polygons
4. Zoom and pan
5. Undo / redo
6. Per-object-type colors
7. Visual layers: background, collisions, flags, selection
8. Visual validation before saving

## 3. Domain requirements

### 3.1 Map entity types

Each entity should have at least:

- `id`: unique identifier within the map
- `type`: entity type

Suggested initial types:

- `boundary`: hard map perimeter
- `rectangle`: rectangular obstacle
- `circle`: circular obstacle
- `polygon`: closed polygonal obstacle
- `flag_blue`: blue flag start position
- `flag_red`: red flag start position

### 3.2 Minimum business rules

1. There must be **exactly one** `boundary`
2. There must be **exactly one** `flag_blue`
3. There must be **exactly one** `flag_red`
4. The `boundary` must be a valid closed polygon
5. Flags must be **inside** the `boundary`
6. Obstacles must be **inside** the `boundary`
7. Every object must have a unique `id`
8. Every object must have a valid `type`
9. Polygons must have at least **3 vertices**
10. Circles must have a radius greater than zero
11. Rectangles must have width and height greater than zero

### 3.3 Considerations for the game runtime

The exported map must be clear enough for the game runtime to:

- load geometry
- compute collisions
- place future spawn or special elements
- serialize the initial state toward clients

Because of that, the editor and the game should share the same JSON contract whenever possible.

---

## 4. Proposed architecture

### 4.1 Overview

The solution should ideally be split into three pieces:

### A. Web editor

HTML/CSS/JavaScript app running in the browser to design maps.

### B. Shared map format

A stable JSON contract generated by the editor and consumed by the game backend.

### C. Game runtime

C# .NET 9 process that loads the map, validates it, and distributes it to connected players.

### 4.2 Recommended technologies

### Simple baseline

- **HTML5 Canvas 2D**
- **JavaScript** or preferably **TypeScript**
- **CSS**
- **JSON** for map persistence
- Browser **File API** for load/save

### Recommended for better maintainability

- **TypeScript** instead of plain JavaScript
- **Vite** as a development environment
- **Canvas 2D** with manual rendering
- lightweight custom geometry utilities

### Optional libraries

- **Konva.js** for 2D editing, selection, and dragging
- **Fabric.js** for editable objects, though less game-map oriented
- **uuid** for IDs if a custom generator is not used
- **zod** or **ajv** for map JSON validation

### Practical recommendation

For this project, the best path is:

- **Canvas 2D + TypeScript + Vite + JSON + custom validation**
- avoiding heavy visual editing dependencies
- because later the gameplay logic and the editor will share geometry concepts more cleanly

## 5. Map data model

### 5.1 General structure

```json
{
  "version": 1,
  "mapId": "arena_alpha",
  "name": "Arena Alpha",
  "width": 1600,
  "height": 900,
  "gridSize": 32,
  "objects": [
    {
      "id": "boundary_001",
      "type": "boundary",
      "points": [
        { "x": 50, "y": 50 },
        { "x": 1550, "y": 50 },
        { "x": 1550, "y": 850 },
        { "x": 50, "y": 850 }
      ],
      "closed": true
    },
    {
      "id": "rect_001",
      "type": "rectangle",
      "x": 300,
      "y": 220,
      "width": 180,
      "height": 90
    },
    {
      "id": "circle_001",
      "type": "circle",
      "x": 900,
      "y": 500,
      "radius": 60
    },
    {
      "id": "poly_001",
      "type": "polygon",
      "points": [
        { "x": 600, "y": 300 },
        { "x": 720, "y": 340 },
        { "x": 680, "y": 450 },
        { "x": 560, "y": 410 }
      ],
      "closed": true
    },
    {
      "id": "flag_blue_001",
      "type": "flag_blue",
      "x": 180,
      "y": 450
    },
    {
      "id": "flag_red_001",
      "type": "flag_red",
      "x": 1420,
      "y": 450
    }
  ]
}
```

### 5.2 Recommended conventions

1. Integer pixel coordinates
2. `(0,0)` origin in the top-left corner
3. `width` and `height` for editable area size
4. `gridSize` for snap and visual guidance
5. `version` for future format evolution
6. A readable unique `mapId`

### Useful improvement

It can be better to separate in JSON:

- `metadata`
- `boundary`
- `flags`
- `obstacles`

That often makes backend consumption easier.

## 7. Interaction design

### 7.1 Main UI tools

Toolbar or side panel actions:

- `Select`
- `Boundary`
- `Rectangle`
- `Circle`
- `Polygon`
- `Blue Flag`
- `Red Flag`
- `Delete`
- `Save JSON`
- `Load JSON`
- `Validate`

### 7.2 Tool flows

#### A. Select

- Click an object to select it
- Show `id`, `type`, and properties
- Allow dragging if included in the current phase

#### B. Boundary

- User clicks to define vertices
- Double click or a close action finishes the shape
- Only one is allowed
- Creating another one should either replace the old one or be blocked

#### C. Rectangle

- First click defines corner A
- Drag or second click defines the opposite corner
- Creates a `rectangle` with `x`, `y`, `width`, and `height`

#### D. Circle

- First click defines center
- Drag or second click defines radius
- Creates a `circle`

#### E. Polygon

- Consecutive clicks add vertices
- Double click closes the polygon
- Minimum 3 points

#### F. Flags

- Select flag tool
- Click on canvas to place
- If a flag of that type already exists, either move it or ask for replacement

#### G. Delete

- Select object and press `Delete`, or use a dedicated delete action
- Optional confirmation for `boundary` or flags

## 8. Validation

### 8.1 Validation while creating

1. Do not allow polygons with fewer than 3 points
2. Do not allow zero or negative radius
3. Do not allow degenerate rectangles
4. Do not allow more than one flag per color
5. Do not allow more than one boundary

### 8.2 Validation before saving

1. Boundary exists
2. Blue flag exists
3. Red flag exists
4. Every entity has a unique `id`
5. Every entity has a valid `type`
6. Every object is inside the boundary
7. JSON can be serialized without loss

### 8.3 Optional advanced validation

1. Detect overlaps between flags and obstacles
2. Detect too-small obstacles
3. Detect self-intersecting polygons
4. Detect objects outside the visible area

## 10. Editor -> game system integration

### 10.1 Proposed flow

1. Developer creates the map in the editor
2. Editor exports `arena_alpha.json`
3. The file is copied into the backend maps directory
4. The .NET 9 process loads the JSON at startup
5. The backend validates the map
6. The backend serializes the map or a reduced version and sends it to clients
7. The client draws the arena and uses the data for collisions or render-only behavior depending on design

### 10.2 Important recommendation

The **server should remain authoritative** for:

- positions
- important collisions
- flag capture
- movement validation

The client can use the map for rendering and visual prediction, but should not decide the final outcome.

## 12. Suggested TypeScript contracts

```ts
export type ObjectType =
  | 'boundary'
  | 'rectangle'
  | 'circle'
  | 'polygon'
  | 'flag_blue'
  | 'flag_red';

export interface Point {
  x: number;
  y: number;
}

export interface BaseObject {
  id: string;
  type: ObjectType;
}

export interface BoundaryObject extends BaseObject {
  type: 'boundary';
  points: Point[];
  closed: true;
}

export interface RectangleObject extends BaseObject {
  type: 'rectangle';
  x: number;
  y: number;
  width: number;
  height: number;
}

export interface CircleObject extends BaseObject {
  type: 'circle';
  x: number;
  y: number;
  radius: number;
}

export interface PolygonObject extends BaseObject {
  type: 'polygon';
  points: Point[];
  closed: true;
}

export interface FlagObject extends BaseObject {
  type: 'flag_blue' | 'flag_red';
  x: number;
  y: number;
}

export type MapObject =
  | BoundaryObject
  | RectangleObject
  | CircleObject
  | PolygonObject
  | FlagObject;

export interface GameMapFile {
  version: number;
  mapId: string;
  name: string;
  width: number;
  height: number;
  gridSize: number;
  objects: MapObject[];
}
```

## 13. Suggested C# .NET 9 contracts

```csharp
public sealed class GameMapFile
{
    public int Version { get; set; }
    public string MapId { get; set; } = string.Empty;
    public string Name { get; set; } = string.Empty;
    public int Width { get; set; }
    public int Height { get; set; }
    public int GridSize { get; set; }
    public List<MapObjectDto> Objects { get; set; } = new();
}

public sealed class MapObjectDto
{
    public string Id { get; set; } = string.Empty;
    public string Type { get; set; } = string.Empty;

    public int? X { get; set; }
    public int? Y { get; set; }
    public int? Width { get; set; }
    public int? Height { get; set; }
    public int? Radius { get; set; }

    public List<PointDto>? Points { get; set; }
    public bool? Closed { get; set; }
}

public sealed class PointDto
{
    public int X { get; set; }
    public int Y { get; set; }
}
```

### Recommended improvement

Later, convert DTOs into internal domain types such as:

- `BoundaryShape`
- `RectangleObstacle`
- `CircleObstacle`
- `PolygonObstacle`
- `FlagSpawn`

That keeps the game engine from depending directly on raw JSON structures.

## 15. Acceptance criteria

The editor will be considered ready when it:

1. Creates a valid boundary
2. Creates rectangles, circles, and polygons
3. Places both flags
4. Gives every entity an `id` and `type`
5. Selects and deletes objects
6. Saves the map as JSON
7. Reloads the saved JSON without data loss
8. Exports a file readable by the .NET 9 backend
9. Detects basic errors before saving
10. Produces a map that can be sent to players by the game system

## 16. Risks and mitigations

### Risk 1: geometry complexity

**Problem:** polygons, selection, and validation can become complex.

**Mitigation:**

- start with basic geometry
- leave advanced vertex editing for a second step
- isolate geometry utilities

### Risk 2: unstable JSON contract

**Problem:** frequent changes can break editor/server compatibility.

**Mitigation:**

- version the format
- centralize serialization
- add compatibility tests

### Risk 3: editor too coupled to runtime

**Problem:** editor starts mirroring internal engine details.

**Mitigation:**

- separate map DTOs from game domain types
- keep a translation layer in the backend

## 19. Final implementation recommendation

For this project, the most solid path is:

1. build the editor in **TypeScript + Canvas 2D**
2. use a **versioned JSON model** from day one
3. maintain a **small custom geometry library**
4. replicate the map contract in the **.NET 9** backend
5. validate both in the editor and on the server

That gives you a fast, simple, and game-compatible foundation.
